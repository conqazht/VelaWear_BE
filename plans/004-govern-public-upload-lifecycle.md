## Why

Authenticated users can call a generic public upload endpoint and choose a folder. The server writes files before any owning entity is updated, so unused files have no durable owner, quota, or cleanup lifecycle. For the current product need, a self-avatar endpoint can bind identity, serialize replacement, and coordinate rollback/commit cleanup without introducing cloud storage.

## Target design

- Add exactly `PUT /api/v1/files/avatar`; its multipart body contains the file only, user comes from JWT, and folder/user ID are never accepted. This is the only customer avatar mutation; BE-001 `/users/me` cannot change `avatar`.
- Acquire a `PESSIMISTIC_WRITE` lock on the user row, store the new local file safely, update `User.avatar`, delete the new file on transaction rollback, and delete the prior local managed avatar only after commit.
- The managed-delete predicate is limited to the configured local avatar namespace. Never delete product/review paths or `http://`/`https://` external avatars. Reuse `UploadProperties.maxSizeBytes` (currently 5 MiB / `5242880`) and `allowedExtensions` (currently `jpg`, `jpeg`, `png`, `webp`), then require signature/MIME validation to agree with the allowed type. Reject traversal, unsupported or mismatched content, and oversized files; do not duplicate these limits as avatar-only constants.
- Reuse the Redis limiter with policy `avatar-upload`: user `5/1h`, IP `30/1h`, global `300/1m`, response code `AUTH_RATE_LIMITED`. Enforce all three buckets before user locking, file storage, or DB mutation. Redis/unconfigured-policy failure is fail-closed exactly like existing auth limiters; every 429 includes the established retry contract, and neither 429 nor fail-closed 503 may create a file or change `User.avatar`.
- Run reconciliation every 6 hours with a 24-hour grace: scan only the managed avatar namespace, batch current `User.avatar` references, and recheck the candidate immediately before deletion. This repairs crash or after-commit cleanup orphans; failures retry next run and emit sanitized events plus `security.avatar.cleanup` with finite `outcome`/`reason` tags.
- Revoke generic `UPLOAD_FILE` from `ROLE_USER`; retain generic product upload only for authorized operator roles.
- Create V23 only as the permission contract: seed the precise self-avatar permission for USER and revoke generic `UPLOAD_FILE` from USER. The preferred one-current-avatar design creates no governance table.

## Done criteria

- Customer avatar upload is self-scoped, serialized, validated, and has defined rollback/after-commit cleanup.
- Redis limits and 6-hour/24-hour-grace reconciliation close churn and crash/cleanup orphan gaps without a table.
- `ROLE_USER` cannot choose arbitrary public upload folders; operator behavior remains intact.
- External URLs are never deleted and local path containment is tested.
- V23 scopes permissions only; no upload-governance table or cloud dependency is added.
- Focused and full verification pass; ADR/API/config docs match the implementation.

## STOP conditions

- Product requires durable preview/unreferenced uploads; that needs a separate ownership/TTL/quota design and plan.
- V23 already exists or migration history has diverged.
- The design deletes external URLs, performs filesystem deletion before DB commit, accepts client folder/user ID, or requires cloud migration.
- Managed deletion can reach outside the configured avatar namespace, the limiter is fail-open, or reconciliation deletes without a final DB-reference recheck.
- User-row lock ordering conflicts with another established transaction; re-plan the ordering first.
