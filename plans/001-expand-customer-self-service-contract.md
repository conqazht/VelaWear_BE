## Why

Customer pages still call generic user-ID resources. `ROLE_USER` therefore holds permissions whose path match does not prove resource ownership, creating an IDOR/cross-account risk. The safe expand/migrate/contract sequence is: add ownership-bound `/me` APIs here, migrate the frontend in FE-001, then revoke legacy permissions in BE-002.

## Target contract

- `PUT /api/v1/users/me` uses a dedicated self-profile DTO containing only `fullName`, `birthDate`, and `gender`; it derives the user from the authenticated JWT. It cannot mutate `User.avatar`. The generic operator `PUT /users/{id}` keeps the existing `UpdateUserRequest`, including `avatar`, until BE-004 makes `PUT /api/v1/files/avatar` the only customer avatar mutation.
- `GET /api/v1/orders/me`, `GET /api/v1/orders/me/code/{orderCode}`, `GET /api/v1/orders/me/{id}`, and `GET /api/v1/orders/me/{id}/status-histories` return only the authenticated user's data. The by-code route preserves the existing `/profile/orders/[code]` frontend URL without a client-side list lookup.
- `GET /api/v1/user-addresses/me`, `GET /api/v1/user-addresses/me/{id}`, `POST /api/v1/user-addresses/me`, `PUT /api/v1/user-addresses/me/{id}`, and `DELETE /api/v1/user-addresses/me/{id}` operate only on the authenticated user's addresses.
- Self-service address creation uses a dedicated request DTO with no `userId` field.
- Cross-account or non-owned identifiers return `404` unconditionally for `GET /orders/me/code/{orderCode}`, `GET /orders/me/{id}`, `GET /orders/me/{id}/status-histories`, and address `GET`/`PUT`/`DELETE /user-addresses/me/{id}`. This avoids both data exposure and ownership enumeration.
- All legacy routes remain behavior-compatible in this expand phase.

## Implementation steps

### 1. Freeze the self-service API contract

Add the routes above to `UserController`, `OrderController`, and `UserAddressController`. Introduce a self-create address DTO without `userId`; keep generic DTOs and endpoints intact.

**Verify**: `.\mvnw.cmd --batch-mode --no-transfer-progress -Dtest=UserControllerTest,OrderControllerTest,UserAddressControllerTest test` → exit 0; route/request/envelope tests pass, including a submitted `avatar` field not changing `User.avatar`.

### 2. Bind every operation to the authenticated account

Resolve the user once from the JWT subject/email through the established service/repository path. Add owner-qualified reads and writes such as order/address ID plus owner ID; never load by ID and authorize only in the controller. Keep transaction boundaries in services and preserve default-address invariants.

**Verify**: `.\mvnw.cmd --batch-mode --no-transfer-progress -Dtest=CustomerSelfScopeIntegrationTest test` → exit 0; self operations succeed, while a second account receives `404` for foreign order ID, foreign order code, that order's status-history route, and address GET/PUT/DELETE by ID.

### 3. Seed additive permissions in V21

Create `src/main/resources/db/migration/V21__seed_customer_self_service_permissions.sql`. Seed precise method/path permissions for the new `/me` routes and assign them idempotently to `ADMIN`, `MANAGER`, `STAFF`, and `USER`, matching the existing self-cart/wishlist convention. Do not remove generic permissions here.

**Verify**: `.\mvnw.cmd --batch-mode --no-transfer-progress -Dtest=SystemSecurityIntegrationTest test` → exit 0; V21 migrates and real `ROLE_USER` receives only the additive self permissions expected in this phase.

### 4. Add production-role ownership tests

Create `CustomerSelfScopeIntegrationTest` using the real `ROLE_USER`, two users, separate orders and addresses, and authenticated requests. Its ownership matrix must cover foreign order ID, foreign order code, status history for the foreign order ID, and foreign address GET/PUT/DELETE, each returning `404`. Extend `OrderControllerTest`, `UserAddressControllerTest`, and relevant user tests. Do not rely only on `TEST_ROLE` from `TestDataFactory`.

**Verify**: `.\mvnw.cmd --batch-mode --no-transfer-progress -Dtest=CustomerSelfScopeIntegrationTest,SystemSecurityIntegrationTest test` → exit 0; two-user isolation and temporary legacy compatibility both pass.

### 5. Synchronize the contract documentation

## Done criteria

- Every target `/me` route is implemented, documented, and ownership-bound below the controller layer.
- Self-service requests cannot choose `userId`; foreign IDs reveal no customer data.
- `PUT /users/me` cannot mutate `User.avatar`; the generic operator DTO remains compatible.
- V21 is additive/idempotent and generic permissions remain for the migration window.
- Focused tests and full backend verification pass.
- The implementation PR states that FE-001 must merge next and BE-002 must wait.

## STOP conditions

- `V21__seed_customer_self_service_permissions.sql` already exists or migration history diverges.
- The frontend cannot adopt the target contract, or a route/DTO decision differs from FE-001 without explicit coordination.
- Ownership can only be enforced in a controller after an unscoped entity load.
- A proposed self-service body still accepts `userId`, or implementation requires revoking legacy access in this PR.
- A self-profile DTO accepts `avatar` or any test can mutate `User.avatar` through `/users/me`.
