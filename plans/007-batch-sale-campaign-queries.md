## Why

Sale-campaign listing maps lazy item collections per campaign, and create/update validates schedule overlap once per requested variant. Both patterns scale queries with page/item size. A two-phase page load and one bulk overlap check can bound database work while preserving the public campaign contract.

## Implementation steps

### 1. Characterize page and overlap behavior

Add fixtures for empty/non-empty pages, multiple campaigns/items, stable item ordering, localized fields, active phases, excluded current campaign on update, duplicate variant input, and exact boundary overlap.

**Verify**: `.\mvnw.cmd --batch-mode --no-transfer-progress -Dtest=SaleCampaignControllerIntegrationTest,SaleCampaignServiceImplLocalizationTest,SaleCampaignConcurrencyIntegrationTest test` → exit 0; payload, totals, ordering, locale, and conflict outcomes are characterized.

### 2. Implement two-phase page loading

Page only campaign roots/IDs with the existing specification and sort. Bulk-fetch details/items for IDs in the page, then reconstruct responses in original page order. Avoid pageable collection fetch joins and preserve count query semantics.

**Verify**: `.\mvnw.cmd --batch-mode --no-transfer-progress -Dtest=SaleCampaignControllerIntegrationTest,SaleCampaignQueryPerformanceIntegrationTest test` → exit 0; totals/order match fixtures and query families remain bounded as page size grows.

### 3. Batch overlap validation

Normalize distinct requested variant IDs and run one overlap query for the whole set and requested time range, excluding the updated campaign where applicable. Map conflicts back to stable domain errors. Keep validation inside the established transaction/lock ordering.

**Verify**: `.\mvnw.cmd --batch-mode --no-transfer-progress -Dtest=SaleCampaignConcurrencyIntegrationTest,SaleCampaignQueryPerformanceIntegrationTest test` → exit 0; one bulk overlap query family handles N items and all phase/boundary outcomes match.

### 4. Bound campaign mutation payloads

Add `@Size(max = 100)` to the item collections in both create and update DTOs and document the limit in the API contract. This matches the repository's existing public maximum-page convention and keeps validation/query/memory work finite; do not introduce a different hidden limit.

**Verify**: `.\mvnw.cmd --batch-mode --no-transfer-progress -Dtest=SaleCampaignQueryPerformanceIntegrationTest,SaleCampaignConcurrencyIntegrationTest,SaleCampaignServiceImplLocalizationTest,SaleCampaignControllerIntegrationTest test` → exit 0; bounded-query assertions and all regression suites pass.

## Done criteria

- Campaign page and overlap validation no longer scale queries linearly with campaigns/items.
- Pagination, response/item order, localization, phases, errors, and lock behavior are unchanged.
- Create/update reject more than 100 items through documented Bean Validation and boundary tests.
- Query-count, regression, concurrency, and full verification pass.

## STOP conditions

- A collection fetch join is proposed with pagination or breaks the count query.
- Bulk validation moves outside the transaction, changes lock order, or changes overlap boundaries/error semantics.
- An active, documented product requirement needs more than 100 items per campaign; stop and revise the contract rather than silently changing the bound.
- The work requires response schema or broader service decomposition.
