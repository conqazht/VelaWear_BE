## Why

Several framework and security failures currently return raw exception messages, while malformed JSON and unsupported methods/media can fall into inconsistent handlers. Clients should branch on finite, documented error codes; internal causes belong only in sanitized server logs linked by request ID.

## Current state and evidence

- `src/main/java/vn/conganh/commercial/exception/GlobalExceptionHandler.java:131-141` returns root-cause or `IllegalArgumentException` text; `144-148` handles otherwise-unclassified errors as generic 500.
- `src/main/java/vn/conganh/commercial/config/SecurityConfig.java:201-232` writes authentication/access-denied exception messages into API responses.
- `src/main/java/vn/conganh/commercial/dto/ApiResponse.java:9-35` already supports a stable `code` field.
- OTP/auth hardening already established business codes such as `OTP_RATE_LIMITED`, `OTP_PROOF_INVALID_OR_EXPIRED`, `AUTH_RATE_LIMITED`, and `SESSION_REVOKED`; these must remain unchanged.

## Target contract

Add/document finite framework/security codes: `REQUEST_BODY_INVALID`, `METHOD_NOT_ALLOWED`, `UNSUPPORTED_MEDIA_TYPE`, `INVALID_REQUEST`, `AUTHENTICATION_REQUIRED`, `ACCESS_DENIED`, and `INTERNAL_SERVER_ERROR`. Map malformed JSON to 400, unsupported method to 405, unsupported media type to 415, unauthenticated to 401, forbidden to 403, and unexpected server failure to 500. Messages are safe, localized only if the existing architecture supports it, and not used as machine identifiers.

## Implementation steps

### 1. Inventory and freeze existing codes

Enumerate every emitted `ApiResponse.code`, status, and consumer. Mark domain/OTP codes as preserved and add the framework/security matrix above to `docs/API_SPEC.md`.

**Verify**: `rg -n "REQUEST_BODY_INVALID|METHOD_NOT_ALLOWED|UNSUPPORTED_MEDIA_TYPE|INVALID_REQUEST|AUTHENTICATION_REQUIRED|ACCESS_DENIED|INTERNAL_SERVER_ERROR" src/main/java docs/API_SPEC.md` → each target code has one documented status/meaning and preserved business codes remain present.

### 2. Add explicit framework handlers

Handle `HttpMessageNotReadableException`, `HttpRequestMethodNotSupportedException`, and `HttpMediaTypeNotSupportedException` explicitly. Convert predictable `IllegalArgumentException` cases to `INVALID_REQUEST` without returning raw text. Keep validation field details only if already safe and documented.

**Verify**: `.\mvnw.cmd --batch-mode --no-transfer-progress -Dtest=GlobalExceptionHandlerTest test` → exit 0; 400/405/415/500 envelopes are stable and contain no parser/root-cause text.

### 3. Stabilize security failures

Update authentication entry point and access-denied handler to emit `AUTHENTICATION_REQUIRED` and `ACCESS_DENIED` in the same envelope. Preserve `SESSION_REVOKED` where the JWT/session validation layer deliberately emits it.

**Verify**: `.\mvnw.cmd --batch-mode --no-transfer-progress -Dtest=SystemSecurityIntegrationTest test` → exit 0; unauthenticated/invalid/revoked 401 and authenticated forbidden 403 retain distinct stable codes.

### 4. Sanitize unexpected-failure logging

Return `INTERNAL_SERVER_ERROR` with a generic message and no cause/stack detail in the client envelope. A sanitized server log may retain the exception stack trace plus correlation context, operation, and finite reason for diagnostics, but must exclude request body, credentials, OTP, proof, token, password, raw email/IP, uploaded content, and unsafe exception-message values.

**Verify**: `.\mvnw.cmd --batch-mode --no-transfer-progress -Dtest=ApiErrorContractIntegrationTest test` → exit 0; the client response contains no cause/stack detail, while sanitized server-log capture retains correlation/diagnostic stack behavior without body, credential, OTP/proof, token, password, raw email/IP, uploaded content, or unsafe exception-message values.

### 5. Synchronize consumers and documentation

Update the exact allowlisted contract documents: `docs/API_SPEC.md`, `docs/PROJECT-STATUS.md`, and `feature/auth/CONTEXT.md`. Record in the PR handoff for external FE-005 that consumers branch on `code` and `Retry-After`, not message text; OpenSpec is outside this PR unless the plan is reconciled first.

**Verify**: `$unsafe = rg -n "exception\.getMessage\(\)|rootCause|getRootCause" src/main/java/vn/conganh/commercial/exception src/main/java/vn/conganh/commercial/config/SecurityConfig.java docs; if ($LASTEXITCODE -gt 1) { exit $LASTEXITCODE }; if ($unsafe) { $unsafe; throw "Raw exception/root-cause response path remains" }` → exit 0 with no matches; `rg` exit 1 means the required zero-match result.

## Done criteria

- Each target framework/security failure has deterministic HTTP status and stable code.
- Raw exception/root-cause text and secrets never reach responses or unsafe logs.
- Existing business/OTP/session codes remain compatible.
- Contract/security tests and full verification pass; documentation is consumable by FE-005.

## STOP conditions

- A frontend flow depends on a raw message and no coordinated migration is approved.
- Proposed handling collapses a deliberate business code into a generic code.
- A test requires logging request bodies, credentials, tokens, OTP/proof, or PII.
- The change requires a wholesale response-envelope migration; split and re-plan it.
